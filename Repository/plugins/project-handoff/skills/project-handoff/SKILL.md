# 项目交接与长程状态流转 (project-handoff)

本技能确保接手对话能够零摩擦承接当前成果、有效决策与确定的第一步，杜绝因长程会话导致的注意力漂移、遗忘已否决路线或重复踩坑。

> **三权分立原则**：  
> - **提醒** 不私自写文件；  
> - **保存** 不私自开新对话；  
> - **新建接续** 必须获得用户的明确确认。

## 二、 评估矩阵：何时应当向用户建议交接

当收到系统注入的检查点消息，或当前任务刚完成一个完整里程碑时，依据当前任务的**客观事实**评估是否建议交接。必须同时满足以下三要素：

| 评估维度 | 核查标准 | 核心理由 |
| :--- | :--- | :--- |
| **1. 安全位置** | 当前文件/文档改动已收拢；测试或后台任务已明确；不存在未归属的半成品 | 避免接手方误以为任务正在进行，造成多方同时修改冲突 |
| **2. 明确后续** | 目标清晰，明确下一步的第一步具体动作与验收标准 | 没有第一步的交接只是存档，新对话接手后仍需向用户反问 |
| **3. 切换收益** | 能明确指出换新会话的具体好处（如剥离前期大规模探索日志、丢弃已否决路线、降低注意力衰减） | 换会话有启动成本，只有当旧上下文的杂质已明显拖累后续执行时才建议切换 |

### 门禁与冷却规则：
- **纯问答 / 任务已完成 / 正在微调细枝末节**：严禁建议交接。
- **严重路线混淆例外**：当且仅当发现并纠正了已核实的目标、版本或重大参数混淆时，可不受步数冷却限制，建议清理上下文重新对齐。
- **用户静默**：若用户曾表示“本任务不提醒”，永久保持静默，直到显式调用。

## 三、 四段式单一事实载体 (SSOT Architecture)

交接材料统一收拢为单个 Markdown 文件（如 `~/.gemini/handoffs/<项目名>/PROJECT_STATE.md` 或工作区已忽略的载体），杜绝碎文件分散：

1. **核心主线区 (Trunk)**：一句话目标、当前基准、已完成证据、接续第一步（100% 聚焦）。
2. **关键上下文锚点与硬约束 (Context Anchors & Invariants)**：核心文件路径、关键实体/符号，以及局部工作区专属约束（若为代码项目则记录关联符号与预检约束），防止接手方偏离边界。
3. **已否决路线与合流教训 (Merged Lessons & Disproven Paths)**：提炼旁支探索中的硬性反面经验与约束（如否决方案及原因），接手方严禁重复踩坑。
4. **附录：已闭环旁支记录 (Archived Branches)**：折叠展示零影响的临时小问题与配置排查记录，完全不污染主线。

---

## 四、 展示规范与建议格式

经评估决定建议交接时，**必须将交接提议放置在当次最终答复正文的第一段**（在成果列表和代码之前），以 `交接建议：` 开头，单段呈现（20~300 字）：

> **交接建议**：本阶段代码分析与方案设计已收拢，后续将进入核心代码重构。当前上下文充斥较多前期探索日志，建议将已确定的架构、已否决路线及第一步整理为交接材料，在新会话中轻量启动。确认后我将为你保存 `PROJECT_STATE.md` 并生成恢复开场白。

### 用户反馈处理分流：
- **用户回复“先不交接”或“继续做”**：从该轮起重新进入 20 步冷却期，不反复打扰。
- **用户回复“本任务不提醒”**：将状态置为 `muted`，本次长任务不再主动提示。
- **用户直接发送常规指令**：常规指令中的“继续”仅视为推进业务，不视为交接批准，正常推进业务。
- **用户确认交接**：立即启动保存流程。
