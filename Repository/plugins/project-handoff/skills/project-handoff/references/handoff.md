# 项目交接实操规范 (SSOT 优化版)

本规范定义了在 Google Antigravity 环境下执行「保存」、「自动接续」与「恢复」的具体标准与工作流。

---

## 核心原则
1. **单一事实载体 (SSOT)**：所有交接信息严格收拢在单一 Markdown 文件内，彻底废弃碎文件目录，杜绝接手方碎片化点读带来的漏读风险。
2. **确定性日志清洗**：在长会话提取交接材料前，优先通过 `transcript_pruner.py` 本地规则脚本（<30ms）剥离无用终端 Dump，压降 70% 噪声。
3. **三权分立**：提醒不写文件，保存不开新任务，新建接续只在用户明确同意具体提议后执行。
4. **首轮只读原则**：接手会话启动的第一轮必须仅进行状态核实（工作区状态、未提交文件、核心上下文锚点），确认无误后才执行实际变更。

---

## 一、 保存流程 (Save Workflow)

当用户说“保存进度”、“整理交接”、“/project-handoff”或确认了交接提议时执行：

1. **执行确定性日志降噪**：
   - 定位当前会话的 `transcript.jsonl`；
   - 运行本地脚本：
     ```powershell
     python ~/.gemini/config/skills/project-handoff/scripts/transcript_pruner.py <transcript_path>
     ```
   - 提取去除冗余输出、包下载进度条和重复大文件之后的精炼事务流。
2. **确定保存路径（遵循 Git 准入规约）**：
   - 优先级 1：用户显式指定的路径。
   - 优先级 2：若当前项目 `.gitignore` 已配置忽略 `PROJECT_STATE*.md`，则保存在项目根目录 `PROJECT_STATE.md`。
   - 优先级 3：若项目有严格 Git 白名单或未忽略该文件，保存在全局目录 `~/.gemini/handoffs/<项目名>/PROJECT_STATE.md`，彻底与工作区 Git 解耦。
3. **结构化提取核心事实（四段式 SSOT）**：
   - 按照 [PROJECT_STATE.template.md](../assets/PROJECT_STATE.template.md) 骨架提取事实：
     - **一、核心主线区 (Trunk)**：一句话目标、当前基准、已完成成果与验证证据、接续第一步（100% 聚焦）。
     - **二、关键上下文锚点与硬约束 (Context Anchors & Invariants)**：核心文件路径、关键实体/符号，以及局部工作区专属约束（若为代码项目则按局部规则记录图谱符号与预检约束），防止接手方偏离边界。
     - **三、已否决路线与合流教训 (Merged Lessons & Disproven Paths)**：提炼旁支探索中的硬性反面经验与约束（如否决方案及原因），接手方严禁重复踩坑。
     - **四、附录：已闭环旁支记录 (Archived Branches)**：折叠展示零影响的临时小问题与配置排查记录，完全不污染主线。
4. **分配编号与标记隔离**：
   - 生成唯一编号：`PH-YYYYMMDD-<工作简称>-<序号>`（例如 `PH-20261016-task-01`）；
   - 使用 `<!-- <简称>-HANDOFF-BEGIN <编号> -->` 和 `<!-- <简称>-HANDOFF-END <编号> -->` 包裹；
   - 若载体已存在其他任务的标记块，**严格保留并仅追加或更新属于当前编号的分节**。
5. **交付成果**：
   - 向用户汇报保存完成的文件绝对路径、交接编号以及可直接复制的恢复开场白。

---

## 二、 自动接续与分流 (Continuation & Handoff Delegation)

只有当用户明确要求“新建并继续”或同意了包含新建任务的提议时触发：

1. **子代理独立接力 (Subagent Delegation)**：
   - 针对独立重任务、深层检索或长跑测试：
   - 主会话调用 `invoke_subagent` 创建独立的子代理；
   - 传入交接编号与开场白，子代理在独立的上下文中进行只读核验；
   - 主会话保持监视，直到子代理反馈结果。
2. **新主会话接力 (Cross-Session Main Chat Handoff)**：
   - 保存完成材料后，生成高信噪比、开箱即用的「恢复开场白」；
   - 引导用户在 Antigravity 开启新 Chat 会话并粘贴该指令。

---

## 三、 零阻碍恢复流程 (Zero-Hop Resume Workflow)

在新会话接收到带有交接编号或指向 `PROJECT_STATE.md` 的恢复指令时执行：

1. **单步全量载入交接载体**：
   - 一次性读取指定的 `PROJECT_STATE.md`（体积仅 2000~3000 tokens，直接置于最清晰的注意力甜区）；
   - **拥有 100% 的主线、关键约束、已否决路线与上下文锚点全局视野，0 次额外 Tool Call 点读开销**。
2. **首轮只读核查 (Read-Only Verification Round)**：
   - 严格不修改任何业务文件；
   - 检查工作区当前状态及未完成项是否与交接记录吻合；
   - 核对材料中记录的关键文件或锚点状态（若局部规则配置了专门检索工具则按局部规则核验）；
   - 检查材料中提及的后台进程或生成文件是否存在。
3. **向用户汇报并启动执行**：
   - 简短汇报：“已完成交接材料核对，工作区状态一致。即将执行第一步：<第一步具体动作>。”
   - 正式开始推进已授权的下一步工作。
